# RAG eval harness review — feat/rag-eval-harness

Review of the retrieval + generation evaluation harness under `evals/` on branch `feat/rag-eval-harness` at commit `408407a6`. Source-and-architecture review; the test suite was not treated as the oracle (it does not run in CI, see below). The question driving the review: is this a proper benchmark harness, and would its published numbers survive scrutiny from Reddit/HN and IR-research communities?

Method: nine independent reviewers (six code-dimension finders over metrics/stats/judge/RAGAS/design/architecture, three adversarial "community" panelists — a statistician, a SIGIR-style IR reviewer, and an HN vendor-benchmark skeptic), each given the 12 defect classes from the prior harness's 63-finding measurement-validity audit (bb-mxle) as a checklist. The automated adversarial-verification phase did not complete (quota), so the five most damaging findings below were re-verified by hand against the source; those are marked CONFIRMED with the exact code.

## Verdict

The **Tier-1 single-arm-pair retrieval scoring core is genuinely well-built** and closes most of the previous audit's defect classes with real delegation and executable tests. But the harness is **not, as committed, a trustworthy instrument for a lilbee-vs-RAGFlow comparison**, and it would not survive external scrutiny in its current state. Two of the three community panels returned "gets torn apart"; the third returned "survives with caveats." The failures are concentrated in exactly the surfaces a skeptic attacks first: the cross-system comparison, the report artifact, and the reproducibility claims.

The single most important point: the parts that grade **one lilbee configuration against another lilbee configuration** (the ablation) are close to sound. The parts that grade **lilbee against RAGFlow** — the comparison the project would actually publish — are broken or unrunnable from committed code.

## Confirmed blockers (hand-verified against source)

**1. The cross-system retrieval comparison scores RAGFlow at 0.0 by construction — no doc-id join exists.**
`cli.py:98` writes qrels keyed on BEIR native document ids. The RAGFlow arm's run file takes `doc_id=chunk["document_id"]` (`collectors.py:164`), which is RAGFlow's internal document UUID. The lilbee arm takes `doc_id=doc["source"]` (`collectors.py:113`), a file path. Neither namespace equals the BEIR ids in the qrels, and there is no committed mapping (UUID→id, path→id) anywhere in the tree. Because `metrics.py` correctly zero-fills unanswered topics, a RAGFlow arm that matches nothing scores a clean 0.0000 across nDCG@10/Recall@20/MRR@10 — which then reads as a decisive, "significant" lilbee win rather than as a namespace bug. There is no `judged@k` / unjudged-rate diagnostic that would catch a 100%-unjudged run before publication. This is the prior audit's fabricated-comparison class re-entering through the collection layer. First HN comment: "how does a RAGFlow UUID ever equal a SciFact doc_id?"

**2. The report renderer crashes in the committed environment.**
`report.py:52` renders every table via pandas `.to_markdown()`, which requires `tabulate`. `tabulate` appears in neither `pyproject.toml` nor `uv.lock` (grep count 0 in both). So `python -m evals.benchmark report` — step 7 of the README's own pipeline — raises `ImportError` in the exact locked environment whose reproducibility the README spends 200 lines defending. Any `report.md` that has ever been produced came from a hand-patched environment that is not the committed one.

**3. Multi-arm reports attribute every row to the first comparison's arm names.**
`_arm_labels` (`report.py:26-30`) reads the arm pair from `meta[0]` only; `_ir_section` (`report.py:88-89`) stamps that single pair onto the column headers of every `ir` row. The report's own text (`report.py:79-80`) says significance is BH-adjusted "across all comparisons in this study," and the committed `manifest.ablation.yaml` declares six arms. To get a family-wide BH across arms you must append multiple arm-pair comparisons to one results file — at which point the dense-vs-w1.0 delta prints under whatever arm the first meta row named. A published number attributed to the wrong system. The advertised PyTerrier multi-arm path (`experiment.py:118` `compare_arms`) that would avoid this is dead code, reachable only from its own test.

**4. The Tier-2 cross-system answer comparison cannot have been produced by committed code.**
README step 5 runs `answer --base-url <ragflow>`. But `_ask` (`cli.py:140-142`) posts `{"question","top_k"}` to a hardcoded `ASK_ROUTE = "/api/ask"` (`cli.py:41`), which is lilbee's route. RAGFlow serves chat completions at `/api/v1/chats/{id}/completions`; `bootstrap_ragflow.py` even prints an `assistant_id` for "the answer step to consume," but no subcommand consumes it. Posting lilbee's payload at RAGFlow 404s and `raise_for_status` kills the run. So the headline "RAGAS scores faithfulness for both arms" is not implementable as committed — the cross-system answer numbers were either never produced or produced by uncommitted, unauditable code.

**5. `generator_delta` averages metrics of opposite polarity into one signed number** (`ragchecker_tier.py:213`). Reported by the RAGAS-tier finder; not hand-verified here but consistent with the code the finder quoted. If confirmed, the RAGChecker "where did the change land" attribution is uninterpretable.

## Important findings (reported by reviewers; representative, not hand-verified unless noted)

- **The test suite runs in no environment and no CI, and six tests are red at the branch tip** (hand-verified). `tests/conftest.py` imports `lilbee`, absent from the evals env; the root env lacks the eval deps. The only working invocation is undocumented (`PYTHONPATH=. uv run --project evals pytest tests/evals --confcutdir=tests/evals`), under which 223 pass and 6 fail — five of them the report-truthfulness tests (title names the arms, judge/scorer versions named, audit section not faked) and one the judge-identity test. Nothing under `.github/workflows` or the Makefile references `tests/evals`. A harness whose entire pitch is measurement validity ships with its validity tests red and ungated.
- **`require_reproducible()` is dead code** (`manifest.py:216`): defined, documented as the reproducibility gate, called by nothing. A manifest with empty `lilbee_commit`/`chunk_size` preregisters and publishes anyway.
- **`provenance.py` has no callers** (`provenance.py:316`): the report's "Machines, timings and cost — read from the pods while the work ran" section (`report.py:237`) renders from `provenance` rows that nothing in the pipeline writes.
- **The RAGFlow arm's "pinned" retrieval knobs never reach the scored path**: similarity threshold / keyword weight / top_n are set on the chat assistant (`bootstrap_ragflow.py:180-186`), but the scored collector POSTs `/api/v1/retrieval` with only question/dataset/page/page_size (`collectors.py:148-157`). The scored arm runs at server defaults, the exact version-drift the pinning claims to prevent.
- **Preregistration constrains additions but not omissions, and not timing**: `stats` rejects undeclared arm/dataset pairs, but nothing checks all declared comparisons are present, and nothing binds collection to a pre-existing fingerprint (`_cmd_collect`/`_cmd_score_ir` never load the manifest). You can run six configs, see the numbers, then write and freeze a manifest declaring the winner, and every check passes. That is not preregistration as OSF/IR reviewers use the word.
- **No pool-bias accounting**: `judged@k` / unjudged rate is computed nowhere, so out-of-pool retrieval on shallowly-pooled BEIR sets (FiQA, TREC-COVID) is scored non-relevant at unmeasured, arm-asymmetric rates. A SIGIR reviewer asks for judged@10 per arm before believing any cross-system delta.
- **MRR@10 tie rule may not match the harness's own doctrine** (strong, not hand-verified): the skeptic argues `RR@10` falls through ir_measures to the bundled msmarco provider, whose ascending-doc_id tie-break is the opposite of the descending rule `runfile.rank_documents` documents. Worth verifying against installed ir_measures internals before publishing MRR.
- **Noise-floor scale error in the report**: `report.py:119-125` presents the per-question judge MAD as a ± band on a difference of means — a scale error the harness's own `scoring.py:40-44` explicitly documents against.
- **"Share of ceiling" can exceed 100%** (`calibration.py:114-121`): judge-vs-mean-of-experts correlation can legitimately beat pairwise expert agreement; the raw ratio is not a disattenuation and prints as a >100% "share of a ceiling."
- **RAGAS tier publishes unpaired means over possibly-disjoint question subsets** (`cli.py:200-213`), the exact bias the sibling retrieval tier fixes with paired qids.
- **The tuned-vs-defaults asymmetry is disclosed only in the README, never in the rendered artifact** that circulates: lilbee runs with title search / neighbor expansion / table extraction / layout / intent-LLM all on against a stock-default RAGFlow, and `render_report` emits significance stars with no arm-configuration footnote.
- **`results.jsonl` ships a raw single-test `significant` flag** (`stats.py:184`) whose own docstring says not to publish it; a dashboard or forum quote reads the uncorrected verdict.
- **Calibration is report-only** with no pass criterion, and nothing ties the SummEval-calibrated judge to the judge that grades the study.

## What is genuinely sound (this is real, and it is most of the retrieval core)

- **Tier-1 metric delegation is real, not claimed.** Cut depths live entirely in the ir_measures measure strings (`metrics.py:33-37`), no harness-side truncation; verified against installed ir_measures 0.4.3 that unanswered qrels topics are zero-filled in both per-query and aggregate paths, pinned by an executable test that asserts the exact aggregate (not just presence). Defect classes 1 and 2 (mislabeled metric, dropped denominator) are closed.
- **One tie rule, correctly chosen and single-sourced** (`runfile.py:48-61`, reused by the PyTerrier frame builder), matching trec_eval's descending-doc_id rule.
- **Document-level depth matching between a chunk-ranked arm and a document arm** (`collectors.py:43-63`, `collapse_hits` cap) — the right construction for class 3.
- **The statistics are the right ones, delegated to scipy, not hand-rolled**: percentile bootstrap, paired sign-flip permutation, Benjamini-Hochberg, with distinct sub-seeds and the p-floor rendered as a bound rather than a fake point estimate.
- **Judge noise floor cannot be structurally zero**: two genuinely different rubric presentations at temperature 0, and a missing replicate raises rather than silently yielding 0.0. Class 5 closed at the root.
- **Self-grading is blocked by a validator, not a convention**: `judge == generator` fails manifest load, and `judge_backend` has no fallback to the answer-authoring model. Class 6 closed on the default path.
- **Checkpoints are content-fingerprinted and refuse mismatched resume**; blind judge gids hash question+arm+replicate+answer. Class 9 closed for answer content.
- **The frozen manifest is tamper-evident** (fingerprint excludes itself and is revalidated on load).
- **The honest-limitations prose is unusually good for a self-benchmark**: the MS MARCO 1.1-judged-passages caveat, derived-vs-native qrels labeling, RAGAS means explicitly not significance-tested, an A/A null control in the ablation manifest.

## Bottom line for the original question

For grading **lilbee against itself** (ablations: which retrieval feature helps), the harness is close to publishable once the report-layer arm-labeling bug (blocker 3), the `tabulate` dependency (blocker 2), and CI wiring are fixed.

For grading **lilbee against RAGFlow** — the comparison that draws public scrutiny — the harness as committed would be torn apart: the doc-id join makes the RAGFlow retrieval arm score zero by construction (blocker 1), the cross-system answer tier is unrunnable (blocker 4), the RAGFlow arm runs unpinned and untuned while lilbee runs fully tuned, and the report that would circulate carries neither the conflict-of-interest footnote nor any judged@k the comparison needs to be believed. None of these are cosmetic; each is the kind of thing a hostile reader finds in the first hour.

Recommended sequencing before any number leaves the building: (1) build and test the doc-id join with a `judged@k` guard that fails a run below a coverage floor; (2) add `tabulate` to the lock and wire `tests/evals` into CI so the six red tests gate; (3) fix report arm-labeling to carry per-comparison arms; (4) either implement the RAGFlow answer route or delete the cross-system Tier-2 claim; (5) render the tuned-vs-defaults asymmetry and judged@k into the artifact itself, not just the README; (6) anchor the preregistration fingerprint (commit/timestamp) before collection, or stop calling it preregistration.
